让模型写一段解释，我们可以直接阅读；但如果要把回答交给程序，用来保存数据、筛选课程或查询系统，就需要约定好它返回的内容。

这篇笔记用一个“课程学习助手”的例子，说明两件事：

- **结构化输出**：让模型按约定整理数据，方便程序读取；
- **工具调用**：让模型提出具体操作，再由程序执行。

前置概念可以参考 [大语言模型基础](<../基础/1. 大语言模型基础.md>)。本文使用独立示例，原文与官方资料放在文末，便于对照阅读。

## 1. 先看一个小功能：整理用户的学习需求

用户对学习助手说：

```text
我刚开始学 Python，每天只能学半个小时。
```

我们希望程序读出三个信息：学什么、目前什么程度、每天有多少时间。

如果模型只回答：

```text
你适合从 Python 入门课程开始，每天安排 30 分钟。
```

人能看懂，但程序还得从这句话里提取信息。更方便的结果是：

```json
{
  "subject": "Python",
  "level": "BEGINNER",
  "minutes_per_day": 30
}
```

程序就可以直接取出 `subject`、`level` 和 `minutes_per_day`，用于后续处理。这就是结构化输出的一个用途：**把自然语言中的信息，整理成有明确字段的数据。**

这里的 `BEGINNER` 是我们为程序约定的值，表示初学者；“半小时”被整理为数字 30。这个结果是演示用的期望输出，真实调用仍需要检查模型是否理解正确。

## 2. 为什么只写“请返回 JSON”还不够

要求返回 JSON，确实能让模型更容易给出这样的结果。但程序还需要明确：

- 字段名固定叫什么；
- 时间应该是数字，还是“半小时”这样的文字；
- 学习程度允许出现哪些值；
- 用户没提供的信息应该怎样表示。

例如，模型也可能给出：

```json
{
  "subject": "Python",
  "level": "刚入门",
  "minutes_per_day": "半小时"
}
```

这是一份合法 JSON，但与我们刚才的字段约定不同：`level` 没有使用程序认识的值，时间也变成了字符串。

还有一种情况是，模型在 JSON 前面加上“下面是整理结果”。人阅读时没问题，直接交给 JSON 解析器却可能失败。

因此，需要分别检查三件事：

| 检查什么 | 具体问题 |
|----------|----------|
| 能否解析 | 是不是一份完整、合法的 JSON |
| 字段是否符合约定 | 名称、类型、必填项和可选值是否正确 |
| 信息是否提取正确 | 用户说每天半小时，结果是否真的是 30 分钟 |

## 3. JSON Mode、JSON Schema 和 Structured Outputs

这三个名字经常同时出现，可以按各自负责的事情来理解。

| 名称 | 做什么 | 在这个例子中的作用 |
|------|--------|--------------------|
| JSON Mode | 模型服务提供的一种 JSON 输出模式 | 约束生成合法 JSON，通常不自动检查我们的具体字段要求 |
| JSON Schema | 描述 JSON 应有的结构和规则 | 约定字段、类型、必填项和学习程度的可选值 |
| Structured Outputs | 根据 Schema 约束模型生成的能力 | 生成时就让结果符合所支持的字段规则 |

可以把 Schema 理解成“这份数据的填写要求”。结构化生成能力则负责在生成时应用这些要求。比如，[Ollama 的官方示例](https://docs.ollama.com/capabilities/structured-outputs)分别展示了只指定 JSON 模式和传入具体 Schema 的用法。

### 3.1 给学习需求写一份 Schema

先确定规则：

- `subject`：字符串，表示学习主题；
- `level`：只能从几个固定值中选一个；
- `minutes_per_day`：整数；用户没说时允许填 `null`；
- 三个字段都必须出现，不能另外增加字段。

对应的 Schema 可以写成：

```json
{
  "type": "object",
  "properties": {
    "subject": {
      "type": "string",
      "description": "用户想学习的主题"
    },
    "level": {
      "type": "string",
      "enum": ["BEGINNER", "INTERMEDIATE", "ADVANCED", "UNKNOWN"],
      "description": "学习程度，无法判断时填写 UNKNOWN"
    },
    "minutes_per_day": {
      "type": ["integer", "null"],
      "description": "每天可学习的分钟数，未提供时填写 null"
    }
  },
  "required": ["subject", "level", "minutes_per_day"],
  "additionalProperties": false
}
```

阅读时，先认识下面几个关键字就够了：

| 关键字 | 含义 |
|--------|------|
| `type` | 数据是什么类型，例如对象、字符串、整数 |
| `properties` | 对象里有哪些字段，各自遵守什么规则 |
| `enum` | 只能从列出的值中选择 |
| `required` | 哪些字段必须出现 |
| `additionalProperties: false` | 不允许增加未声明的字段 |
| `description` | 帮助模型和开发者理解字段含义 |

这些规则属于 [JSON Schema](https://json-schema.org/learn/getting-started-step-by-step) 的结构描述。`description` 是说明文字；“没有时间信息时填 null”这样的含义，仍然需要模型理解，不能只靠一段描述就保证提取正确。

### 3.2 没提供的信息，怎样表达

如果用户只说“我刚开始学 Python”，没有提到时间，可以约定返回：

```json
{
  "subject": "Python",
  "level": "BEGINNER",
  "minutes_per_day": null
}
```

这时，“时间未知”与“少了一个字段”是两种不同情况。前者是正常的数据状态，后者不符合这里要求三个字段都出现的约定。

程序也可以根据 `null` 继续询问“每天大概能学多久”，而不是随意给用户填一个时间。

### 3.3 有了 Schema，怎样让它生效

使用支持结构化输出的模型服务时，要按照接口要求，把 Schema 放进相应的请求配置里。只在本地写好 Schema 文件，还不会影响模型生成。

不同服务支持的规则可能不同。例如，某些服务只支持 JSON Schema 的一部分关键字。入门时先用简单的对象、字段类型和枚举，确实需要更复杂的规则时再查能力说明。

此外，还要处理拒绝回答、生成被截断和请求失败等情况。接口支持结构化输出，并不意味着每次业务任务都会成功，相关说明见 [Claude 的结构化输出文档](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)。

## 4. 程序接收模型结果后，怎样检查

对于有 Java 基础的开发者，可以把这一步类比成：收到接口响应后，先反序列化成 DTO，再做字段校验和业务检查。

例如，“每天可学习时间”即使是整数，也可能被错误地填成负数；字段格式合格，并不代表适合直接用于课程推荐。

### 4.1 一个小型校验示例

下面用 Python 标准库演示接收过程。它只检查本例中的几条规则，方便看清步骤；项目中的复杂 Schema 可以交给现成的校验库处理。

```python
import json


def read_learning_need(raw_text):
    data = json.loads(raw_text)  # 文本不是合法 JSON 时会抛出异常

    if not isinstance(data, dict):
        raise ValueError("结果必须是一个 JSON 对象")

    expected = {"subject", "level", "minutes_per_day"}
    if set(data) != expected:
        raise ValueError("字段缺失或存在多余字段")

    if not isinstance(data["subject"], str) or not data["subject"].strip():
        raise ValueError("学习主题必须是非空字符串")

    levels = {"BEGINNER", "INTERMEDIATE", "ADVANCED", "UNKNOWN"}
    if not isinstance(data["level"], str) or data["level"] not in levels:
        raise ValueError("学习程度不在约定范围内")

    minutes = data["minutes_per_day"]
    if minutes is not None:
        if type(minutes) is not int or minutes <= 0:
            raise ValueError("每天学习时间必须是正整数或 null")

    return data


raw_text = '{"subject":"Python","level":"BEGINNER","minutes_per_day":30}'
need = read_learning_need(raw_text)
print(need["subject"], need["minutes_per_day"])
```

这段代码验证了结构和一些基本规则；它还不能判断原始用户是否真的说过每天有 30 分钟。内容是否忠实于输入，需要另外通过样例和结果核对。

### 4.2 校验失败后怎么办

可以先说明具体错误，让模型尝试修正。例如，发现时间被写成了文字，可以反馈：

```text
上次结果中的 minutes_per_day 类型不符合要求。
请根据原始用户需求重新整理：时间使用整数分钟，未提供时填 null。
只返回符合字段约定的 JSON。
```

重试时要保留原始需求，并限制次数。若信息本来就没有提供，应询问用户；若是输出被截断，应先检查生成长度；若是服务暂时不可用，则需要按应用要求返回失败提示或稍后处理。

## 5. 工具调用：让模型使用实际功能

现在把任务增加一步。用户说：

```text
我刚开始学 Python，每天只能学半小时，帮我查查有哪些合适的课程。
```

整理出学习需求还不够。要推荐课程目录中真实存在的课程，系统还需要查询目录。

**Function Calling（函数调用），也常称为 Tool Calling（工具调用），让模型根据任务生成函数名和参数，再由程序执行对应功能。**

例如，后端可以提供一个工具：

| 工具信息 | 内容 |
|----------|------|
| 名称 | `find_courses` |
| 用途 | 从现有课程目录筛选课程，只查询、不报名 |
| 参数 `subject` | 学习主题，例如 Python |
| 参数 `level` | 课程难度，例如 BEGINNER |
| 参数 `max_minutes` | 单节课程的最长分钟数 |

调用模型时，应用需要按照接口要求提交工具名称、用途描述和参数 Schema。模型根据这些说明，判断是否要使用工具，以及参数怎样填写。

### 5.1 模型先提出调用请求

下面用简化数据展示过程，具体的消息封装以所用模型接口为准：

```json
{
  "call_id": "course_lookup_01",
  "name": "find_courses",
  "arguments": {
    "subject": "Python",
    "level": "BEGINNER",
    "max_minutes": 30
  }
}
```

这份数据表示模型希望调用 `find_courses`。**此时还没有查到任何课程。**

### 5.2 程序执行查询

应用接收到请求后，找到事先注册的 `find_courses` 处理方法，检查参数，再去查询数据库或课程服务。

例如，这个工具内部可能调用普通 HTTP 接口：

```http
GET /api/courses?subject=Python&level=BEGINNER&maxMinutes=30
```

`find_courses` 是提供给模型使用的工具名称，HTTP 接口则是实际业务服务的入口。两者之间如何映射，由应用实现。

应用应只执行已经注册的工具，按规则检查参数与访问权限。若用户没说学科或时间，可以先询问，而不是让模型随意补齐后直接执行。

### 5.3 把结果交回模型，再回答用户

假设目录返回了下面这条课程记录。记录是演示数据，不是实际推荐：

```json
{
  "call_id": "course_lookup_01",
  "result": {
    "courses": [
      {
        "course_id": "PY-BASIC-01",
        "title": "Python 变量与条件判断",
        "lesson_minutes": 25
      }
    ]
  }
}
```

应用把查询结果按接口协议与对应调用关联，并连同必要的对话一起交回模型。模型再组织成用户能读懂的回答：

```text
目录里有一节“Python 变量与条件判断”，时长 25 分钟，
符合你每天半小时的安排。
```

整个过程就是：

```text
用户提出需求
      ↓
模型提出：调用 find_courses，使用这些参数
      ↓
应用执行课程查询
      ↓
应用将查询结果交回模型
      ↓
模型根据结果回答用户
```

这里由自己的后端执行查询。有些服务也提供托管工具，由服务商的运行环境执行；区别在于谁运行工具。模型请求、工具执行和结果回传的说明见 [Claude 的工具使用文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)。

## 6. 结构化输出和工具调用怎样选择

可以先问自己：**这次只需要整理已有信息，还是还需要做一次实际查询或操作？**

| 需求 | 可以使用什么 |
|------|--------------|
| 从用户的话中提取主题、程度和时间 | 结构化输出 |
| 将一段笔记整理成固定字段的卡片 | 结构化输出 |
| 查询当前课程目录中有哪些合适课程 | 工具调用，由程序实际查询 |
| 把选定课程加入用户学习计划 | 工具调用，并由后端检查用户意图、权限和业务状态 |

它们也可以一起使用：先把需求整理成结构化数据，再查询课程；查询后，也可以要求模型把最终建议整理成指定结构。

但并非每次都必须先单独做一次提取。简单任务中，模型也可以直接从用户需求生成工具参数。怎样安排步骤，应看任务需要。

## 7. MCP、HTTP API 和 Skill 在这里分别做什么

学习工具调用时，经常会遇到这些名字，可以把它们放回课程助手中理解：

| 名称 | 在例子中做什么 |
|------|----------------|
| Function Calling / Tool Calling | 模型表达“调用课程查询工具，参数是这些” |
| HTTP API | 后端对外提供的实际课程查询接口 |
| MCP | 应用与外部工具服务发现能力、发起调用和接收结果的一种协议 |
| Skill | 可复用的任务说明，例如怎样分析学习目标、查找课程并组织建议 |

它们可以按需组合，不是每次都必须依次经过的四个步骤。例如，应用可以直接把本地查询函数提供为工具，不一定先接入 MCP；Skill 也可以只指导如何整理文本。

这些概念在 [AI Agent 基础](<../基础/2. AI Agent 基础.md>) 中有更完整的说明。刚开始做应用时，先掌握模型输出、程序校验、实际执行和结果回传这条过程即可。

## 8. 先完成一个能核对的小功能

可以从上面的学习需求提取开始，准备几条固定样例：

| 用户输入 | 希望检查什么 |
|----------|--------------|
| 我刚学 Python，每天半小时 | 是否提取为初学者、30 分钟 |
| 我刚学 Python，时间还没定 | 未知时间是否填写 null |
| 我学过基础，想继续学，但没说具体主题 | 是否能发现缺少信息并继续询问 |
| 每天只能学 0 分钟 | 是否触发业务检查或进一步确认 |
| 给一段和学习完全无关的话 | 是否说明无法提取，而不是编出一份计划 |

Schema 可以约束字段，却不能代替这些任务检查。例如，当前例子将学习主题设为字符串，但没有单独设计“输入与学习无关”的处理状态。准备正式接入时，就需要补上这种分支，而不是强迫模型为每个输入都生成一份学习计划。

随着功能扩展，还可以记录 Prompt 与 Schema 的版本、失败原因和处理结果。涉及真实查询或写入时，则要继续测试无结果、参数不全、超时和重复请求等情况。

## 9. 速查表

| 概念 | 先记住的作用 |
|------|--------------|
| JSON Mode | 约束使用合法 JSON 格式，具体字段仍需检查 |
| JSON Schema | 约定字段、类型、可选值和必填项 |
| Structured Outputs | 根据所支持的 Schema 约束生成结果 |
| Function Calling | 模型生成函数名和参数 |
| 工具执行层 | 接收调用请求，校验并运行实际功能 |
| 工具结果回传 | 把实际执行结果与对应调用关联，再提供给模型 |
| 程序校验 | 检查结构、字段和业务规则 |

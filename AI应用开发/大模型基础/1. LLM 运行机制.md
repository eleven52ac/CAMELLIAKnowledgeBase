学习 AI 应用开发时，我们会把用户的问题交给模型，再把模型的回答展示出来。但真正动手后，很快就会遇到几个问题：为什么同样的问题回答不一样？为什么输入一大段资料后变慢了？为什么要求返回 JSON，结果却只写了一半？

这篇笔记从一个简单功能出发：**让模型给客户反馈分类**。通过这个例子，理解一次模型调用中会发生什么，以及开发时需要关注哪些设置。概念总览可以先看 [大语言模型基础](<../基础/1. 大语言模型基础.md>)。

## 1. 模型收到问题后，是怎样生成回答的

假设我们正在开发一个客服系统，希望模型判断反馈属于哪一类，并提取一句话摘要。

可以给模型这样的输入：

```text
请将客户反馈分为以下四类之一：账号、支付、物流、其他。
用 JSON 返回 category 和 summary 两个字段，只提取反馈中已有的信息。

客户反馈：
我刚改了密码，现在还是登录不上。
```

一个符合要求的回答示例是：

```json
{
  "category": "账号",
  "summary": "修改密码后仍然无法登录"
}
```

模型会根据输入和已经生成的内容，逐步生成后面的文本。可以先把过程理解成：

```text
 你提供任务说明和客户反馈
            ↓
 模型处理这次输入
            ↓
 生成一小段内容，再接着生成下一段
            ↓
 回答结束，返回结果和用量信息
```

上图展示的是便于理解的生成过程。模型实际处理的基本单位叫 Token，我们下一节再介绍。

### 1.1 “等它开始回答”和“等它全部说完”有什么区别

在模型服务的文档中，可能会看到两个词：

| 名称 | 可以怎样理解 | 与应用有什么关系 |
|------|--------------|------------------|
| Prefill（预填充） | 先处理你已经发过去的内容 | 输入越多，开始回答前要处理的工作通常也越多 |
| Decode（解码） | 根据已有内容，继续生成回答 | 回答越长，通常需要生成越久 |

例如，发送一整份客服手册，只让模型回答一句话，等待可能主要花在处理输入上；只输入一个问题，却让它写一份长报告，后续生成就可能占用更多时间。

实际等待还会受到网络、服务负载和请求排队影响。排查慢在哪里时，要分开观察这两个阶段。

> [!tip] 开发时先记住
> 输入长度和回答长度都会影响调用。输入很多、输出很少，也不代表这次调用一定很快。

## 2. Token 是什么，为什么不能直接按字数算

**Token 可以先理解成模型读写文字时使用的“小片段”。** 它可能是一个词、词的一部分、标点或其他片段，具体怎样切分由模型使用的分词器决定。

所以，一个汉字不一定对应一个 Token，一个英文单词也不一定只占一个 Token。同一段文字，换一个模型，统计结果还可能变化。

对于应用开发，先区分两种用量：

| 类型 | 包含什么 | 客服分类中的例子 |
|------|----------|------------------|
| 输入 Token | 这次交给模型的内容 | 分类要求、客户反馈、附带的资料和历史消息 |
| 输出 Token | 模型生成的内容 | category、summary 及相关 JSON 内容 |

### 2.1 为什么用户只写一句话，输入用量却很多

因为应用发给模型的，可能不只有用户的这一句话。

例如，后端还可能补上：

- “只能分为账号、支付、物流、其他”的任务规则；
- JSON 字段要求和工具说明；
- 前几轮的聊天记录；
- 从知识库查到的参考材料。

这些内容加起来，才接近模型真正收到的输入。消息格式本身也可能带来额外开销。

### 2.2 开发时怎样查看用量

许多模型接口会在响应中返回 `usage`，用于说明本次处理了多少输入和输出 Token。**实际调用后，应查看服务返回的用量，而不是用字数直接代替。**

请求前需要估算时，可以使用对应模型的分词器或官方计数功能。Token 的切分方式见 [Hugging Face 的分词器教程](https://huggingface.co/learn/llm-course/en/chapter2/4)，用量说明也可以参考 [DeepSeek 官方文档](https://api-docs.deepseek.com/quick_start/token_usage/)。

如果发送的是图片或音频，还需要查看相应的计量规则，不能只数随同发送的文字。

## 3. 上下文窗口：这次能给模型看多少内容

**上下文，就是模型回答这次问题时能够使用的材料。上下文窗口，就是这些内容能够占用多大的空间，通常用 Token 衡量。**

在客服分类中，上下文可能包含：

```text
分类要求 + 历史对话 + 客户反馈 + 必要的参考资料
```

### 3.1 需要给回答留出空间

假设某模型服务的输入和输出共用一个 8000 Token 的窗口。我们打算让它最多生成 1000 Token，那么输入就不能把 8000 全部占满。

可以先这样计算：

```text
总空间：8000 Token
留给回答：1000 Token
留给输入：最多 7000 Token
```

实际开发时还可以留一些余量。这个例子用于说明分配方法；有的服务会分别限制输入和输出，要以具体接口的规则为准。

有些推理模型还会先做内部推理，再给出可见回答。如果它们共用生成预算，即使最后展示的文字很短，也可能已经用了不少输出预算。

### 3.2 聊久了为什么会“忘记”

聊天记录不断增加，应用可能无法把全部历史都放进下一次请求，于是会删去较早的消息，或者把它们缩成摘要。

因此，用户在聊天界面上还能看到一段话，不代表模型这次仍然收到了它。需要模型记住的关键信息，要由应用在后续请求中保留或重新提供。

### 3.3 资料放得越多，回答就越好吗

不一定。比如为了给一条登录反馈分类，却把退款制度、仓储规则和全部客服聊天记录都放进去，可能只会增加等待、费用和干扰。

更实用的做法是：先提供完成任务真正需要的材料；发现缺少信息，再有针对性地补充。

还要区分两个问题：**请求超出了窗口，和请求没有超限但模型漏看信息，是两回事。** 请求超限可能直接报错；即使长度合法，模型也可能没有正确利用其中的内容。[Lost in the Middle](https://arxiv.org/abs/2307.03172)研究了长输入中信息位置对部分模型表现的影响。

## 4. 输出长度：为什么回答或 JSON 只写了一半

最大输出长度这一类设置，通常叫 Max Tokens，具体参数名因服务而异。它规定模型这次最多生成多少 Token，不代表必须写满。

假设给客服分类任务的输出空间太小，返回内容可能停在这里：

```text
{
  "category": "账号",
  "summary": "修改密码后
```

这段结果还没写完，程序直接解析就会失败。

### 4.1 遇到截断时先检查什么

1. 查看接口返回的结束原因，确认是不是达到生成上限；
2. 检查预留的回答长度是否足够；
3. 如果使用推理模型，确认生成预算是否还包括推理部分；
4. 如果设置了停止词，检查它是否误触了正常内容。

**Stop Sequences（停止序列）** 可以理解为“生成到这些内容时就停下来”。如果把空行等正常回答里也会出现的内容设为停止条件，就可能提前打断回答。初学时通常可以先使用默认配置。

### 4.2 返回了 JSON，也要检查能否使用

处理结果时，可以按顺序做三件事：

```text
确认这次生成正常完成
        ↓
确认 JSON 完整，字段符合约定
        ↓
确认分类和摘要与客户反馈相符
```

模型也可能返回一份格式完整、内容却错误的 JSON。所以，“能解析”和“回答正确”需要分别检查。

## 5. 采样参数：为什么同样的问题回答不一样

模型在生成下一步内容时，通常不只有一个候选，而是会为不同候选计算分数。**采样参数，就是影响它怎样从候选中做选择的设置。**

先理解它们各自的作用，再决定是否需要调整。

### 5.1 Temperature：回答的变化有多大

**Temperature（温度）** 会影响候选被选中的机会：

- 温度较低：原本概率高的候选更容易被选中，回答通常比较集中；
- 温度较高：其他候选有更多机会，措辞和内容通常更有变化。

例如，让模型反复概括同一条客户反馈，可能得到“改密码后无法登录”和“修改密码后仍登录失败”。任务结果可能相同，表达却有变化。

客服分类通常更关注分类准确、字段稳定；写宣传文案则可能希望多一些表达变化。选择配置时，要根据任务结果判断。

> [!warning] 低温度不等于不会出错
> 温度影响的是怎么选内容，不会让模型自动获得正确答案。一个错误答案，也可能被模型反复、稳定地生成。

有些接口支持把温度设为 0，按较确定的方式生成；另一些接口的设置方式不同。即使使用低温度，也不能把所有服务的输出都当成逐字一致。

### 5.2 Top-k：只从前几个候选中选

为了看清规则，假设某一步只有 A、B、C 三个候选，概率分别为 60%、30%、10%。这里的数字只是教学示例。

如果 `top_k = 2`，就保留排名前两位的 A、B，再从中选择。它关注的是**保留几个候选**。

### 5.3 Top-p：保留累计概率达到要求的候选

仍然使用这个例子，如果 `top_p = 0.8`：

```text
A：60%            还没达到 80%
A + B：90%       达到 80%，保留 A、B
```

如果另一轮的第一名本身就占了 90%，按照这个简化规则，达到 80% 时可能只需要保留第一名。

所以，Top-p 保留的数量会变化；Top-k 则直接按数量来选。它们都是筛选生成候选，不是在替我们核实事实。相关机制可以参考 [Hugging Face 的解码方式介绍](https://huggingface.co/blog/how-to-generate)。

### 5.4 Penalty：减少机械重复

如果模型总在重复相似词句，有些服务提供重复惩罚参数：

| 参数 | 可以怎样理解 |
|------|--------------|
| Repetition Penalty | 调整已经出现过的 Token 的得分，具体方式取决于实现 |
| Presence Penalty | 根据某个 Token 是否出现过进行调整 |
| Frequency Penalty | 根据出现次数进行调整 |

但有些重复是必要的。例如，多条分类结果里可能都需要出现 `category` 和 `summary`。惩罚设置过强，反而可能影响正常输出。

这些参数不一定都被所选服务支持。入门时先保留默认值，确实发现重复问题后再做对比，比一开始同时修改所有参数更容易判断原因。

## 6. 流式输出：为什么能边生成边显示

聊天界面中，回答常常会一点点出现，这就是流式输出的常见展示方式。

可以用“等完整封信写好再寄出”和“写出一部分就先交给你看”来理解两种返回方式：

| 返回方式 | 用户看到什么 |
|----------|--------------|
| 等完整回答后返回 | 等一段时间，再看到整份结果 |
| 流式返回 | 先看到部分内容，然后继续显示后面的内容 |

流式主要改善的是等待时的体验。它不会自动减少模型要生成的内容，也不会自动省钱。

### 6.1 分开看两个等待时间

- **多久开始有内容**：这与网络、排队和处理输入等有关，常见相关指标是 TTFT，即首个 Token 到达时间；
- **多久全部完成**：还受到最终回答长度、后续生成速度等影响。

如果输入了一份很长的手册，模型需要先处理它。开启流式之后，也可能仍要等一段时间才开始显示回答。

### 6.2 JSON 接收完整后再处理

对于客服分类，前端可以显示接收进度，后端则应等结果完整、生成正常结束后，再解析和校验 JSON。只收到前半段时，它还不是一份可以直接使用的结果。

实际流式响应会带有增量和结束事件，格式可参考 [Claude 的流式输出文档](https://platform.claude.com/docs/en/build-with-claude/streaming)。

## 7. 费用和缓存：怎样让调用更合适

### 7.1 输入和输出通常分别计量

很多模型服务会分别统计输入和输出 Token，并采用各自的价格。回答越长，生成用量也可能越多；每次带上大量无关资料，也会增加输入用量。

下面用一组**虚构价格**演示计算方法：

| 项目 | 用量 | 假设单价 | 本次费用 |
|------|------|----------|----------|
| 输入 | 2000 Token | 每百万 Token 2 元 | 0.004 元 |
| 输出 | 1000 Token | 每百万 Token 6 元 | 0.006 元 |
| 合计 | | | **0.01 元** |

实际计算要使用所选服务的当前价格，并查看它如何统计缓存和推理用量。用量里有些字段是总数，有些是其中的部分，不应把同一部分重复相加。

### 7.2 多次使用相同内容，可以利用前缀缓存

假设我们每天要处理很多条客户反馈，分类规则和 JSON 字段要求都相同，只是最后的反馈不同：

```text
请求 A：相同的分类规则 + 相同的字段要求 + 反馈 A
请求 B：相同的分类规则 + 相同的字段要求 + 反馈 B
```

如果模型服务支持 **Prompt Caching（提示词缓存，也常称前缀缓存）**，满足条件时，就可以复用前面相同内容的部分处理结果，减少重复计算，并可能降低相应输入费用。

开发时，可以把稳定的任务规则放在前面，把每次变化的客户反馈放在后面。缓存是否命中、有效期和收费方式，要看服务本身的说明，例如 [Claude 的缓存文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。

### 7.3 三种“缓存”别混在一起

| 名称 | 简单理解 |
|------|----------|
| KV Cache | 模型生成过程中复用前面算过的部分结果，通常由推理服务处理 |
| Prompt Caching | 不同请求复用相同输入前缀的部分处理结果 |
| 应用结果缓存 | 我们自己的系统把已经得到的答案保存下来，在适合的情况下复用 |

前两种缓存都不意味着模型可以直接返回上一次的完整答案。命中的输入内容也仍然属于模型这次能看到的上下文。

## 8. 刚开始做应用时，怎样使用这些知识

继续以客服分类为例，可以按下面的顺序实践：

1. **先打通一个最小功能**：输入一条反馈，拿到分类与摘要；
2. **准备几条固定样例**：覆盖账号、支付、物流和难以判断的情况，核对是否分对；
3. **检查输出完整性**：确认 JSON 能解析、字段齐全、内容没有编造；
4. **观察用量与时间**：查看输入和输出 Token，记录开始返回及全部完成的时间；
5. **根据实际问题调整**：资料太多就精简，输出被截断就检查长度，结果波动明显再比较采样设置。

一次先改变一个主要设置，再比较这些固定样例，才能知道变化带来了什么效果。不要只看某一次回答“感觉不错”，还要看多次调用后是否稳定完成任务。

### 8.1 遇到问题时，先看哪里

| 遇到的问题 | 先检查什么 |
|------------|------------|
| 输入用量比想象中多 | 是否带了很长的规则、资料或聊天历史 |
| 很久才开始回答 | 输入长度、网络、服务排队等情况 |
| JSON 或长回答没写完 | 结束原因、输出上限、停止词 |
| 同一个问题表达不一样 | 采样设置、实际输入、模型版本 |
| 回答很稳定，但不正确 | 任务是否说清楚、信息是否充分、模型表现是否合适 |
| 总是重复内容 | 输入是否重复，生成长度和惩罚设置是否合适 |

### 8.2 遇到暂时用不到的术语怎么办

有时文档还会提到下面这些词，先知道它们大致在说什么就够了：

| 术语 | 入门时先这样理解 |
|------|------------------|
| Tokenizer | 把文字切成模型处理片段的分词器 |
| Logits | 模型给下一步候选内容计算的分数 |
| Softmax | 把这些分数转换为概率的一种计算方法 |
| Logprobs | 关于生成 Token 概率的信息，不能直接当成答案正确率 |
| Schema | 约定输出应有哪些字段、类型和必填项的规则 |

这些术语背后有更细的数学和实现细节。等应用中出现具体需求，再沿着相应问题学习，会更容易理解它们的作用。

## 9. 速查表

| 概念 | 先记住这件事 |
|------|--------------|
| Token | 模型读写内容的单位，不等于字数 |
| 上下文窗口 | 模型这次能处理多少内容，需要关注输入和生成的限制 |
| 最大输出长度 | 限制回答最多生成多少，太小可能截断 |
| Temperature | 影响候选选择的集中程度，低温度也可能答错 |
| Top-k / Top-p | 影响从哪些候选中选择下一步内容 |
| Penalty | 用于调整重复倾向，先默认、有问题再比较 |
| 流式输出 | 能提前看到部分回答，但不自动减少总用量 |
| usage | 核对本次实际用了多少输入和输出 Token |
| 前缀缓存 | 重复的输入前缀可能复用部分计算 |

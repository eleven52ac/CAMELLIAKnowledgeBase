## 1. 核心机制

HashMap 的扩容由**负载因子**控制，默认值 `0.75`。当元素数量超过 `容量 × 0.75` 时触发扩容。

- 初始容量 16，阈值 = 12，存第 13 个元素时扩容；
- 扩容规则：容量**直接翻倍**，16 → 32 → 64，始终保持 2 的幂次；
- 扩容后所有元素要重新分配位置，这个过程叫 **rehashing**；

## 2. 元素搬迁

> [!important] 核心结论（JDK 8 优化） 扩容时元素只会落在两个位置
> 
> 1. **原位置不变**
> 2. **原位置 + 旧容量**
> 
> 只需看 `hash` 的第 N 位（旧容量对应的高位）是 0 还是 1。

### 2.1. 位运算原理

数组长度始终是 2 的幂次，定位下标用 `(容量 - 1) & hash`：

```
16 - 1 = 15，二进制：001111
32 - 1 = 31，二进制：011111
```

两者差别仅在**高位多了一个 1**。所以只需判断 `hash & oldCap` 的结果：

|结果|含义|新位置|
|---|---|---|
|`== 0`|高位为 0，吃不到新容量的高位|原位置不变|
|`!= 0`|高位为 1|原位置 + oldCap|

### 2.2. 源码体现

```java
// 链表扩容迁移（JDK 8）
Node<K,V> loHead = null, loTail = null; // 低位链（原位置）
Node<K,V> hiHead = null, hiTail = null; // 高位链（原位置+oldCap）
do {
    next = e.next;
    if ((e.hash & oldCap) == 0) {
        // 留在原位
        if (loTail == null) loHead = e;
        else loTail.next = e;
        loTail = e;
    } else {
        // 搬到新位置
        if (hiTail == null) hiHead = e;
        else hiTail.next = e;
        hiTail = e;
    }
} while ((e = next) != null);

if (loTail != null) { loTail.next = null; newTab[j] = loHead; }
if (hiTail != null) { hiTail.next = null; newTab[j + oldCap] = hiHead; }
```

链表数据**一次性计算完，整体搬运**，不是逐个重新取模。

## 3. 为什么负载因子是 0.75

这是**时间和空间的权衡**：

- 太小（如 0.5）：空间利用率低，内存浪费；
- 太大（如 0.9）：桶位冲突概率高，链表变长，查询退化为 O(n)；
- `0.75`：根据泊松分布分析，链表长度超过 8 的概率不到千万分之一，空间与查询效率平衡最佳。

## 4. 扩容的性能考量

- 每次扩容遍历所有元素重新计算位置，是 **O(n)** 操作，频繁扩容性能明显下降
- **最佳实践**：预估数据量，创建时指定合适初始容量

```java
// 要存 100 万条数据：100w / 0.75 ≈ 134w，向上取到 2^21 = 2097152
new HashMap<>(2097152);
```

> 指定初始容量会被自动调整到最近的 2 的幂次：传 100 → 实际 128，传 1000 → 实际 1024。

## 5. JDK 1.7 vs 1.8 扩容对比

| 特性    | JDK 1.7          | JDK 1.8        |
| ----- | ---------------- | -------------- |
| 迁移算法  | 每个元素重新计算 hash 取模 | 位运算判断高位，只有两种位置 |
| 链表迁移  | **头插法**，会改变顺序    | **尾插法**，保持原顺序  |
| 多线程问题 | 可能成环导致**死循环**    | 不会成环，但仍可能丢数据   |
| 树化    | 无                | 链表超过 8 转红黑树    |

## 6. 扩展

**Q：扩容时链表和红黑树处理方式一样吗？**

> 不一样。链表直接按高位 bit 分成两条链表，分别挂到原位置和新位置。红黑树也按高位 bit 分成两棵树，但分完后要检查节点数量，如果 `≤ 6` 就退化回链表，否则保持树结构。退化阈值 6 和树化阈值 8 差了 2，是为了**避免频繁在链表和树之间来回转换**。

**Q：HashMap 扩容时线程安全吗？**

> 不安全。JDK 1.7 头插法，两个线程同时扩容可能把链表搞成环，导致 `get` 无限循环、CPU 打满。1.8 改成尾插法解决了成环问题，但两个线程同时 `put` 仍会丢数据（一个线程的数据被另一个覆盖）。多线程场景要用 `ConcurrentHashMap`。

**Q：能不能让 HashMap 不扩容？**

> 可以，把负载因子设成 `Integer.MAX_VALUE`，但不推荐。负载因子太大会导致大量哈希冲突，链表越来越长，查询效率急剧下降。JDK 8 虽然有红黑树兜底，但树化也有开销，且元素分布不均匀时某些桶特别长。正确做法还是预估数据量，给一个合理的初始容量。
